# E2E Test Infrastructure & Specification (`TEST_INFRA.md`)

## 1. Test Philosophy & Principles

Project Ripple ("Runs with Gates" — Hosted Multi-Agent Collaborative Workspace) follows an **opaque-box, requirement-driven End-to-End (E2E) testing discipline**:

1. **Opaque-Box Surface Verification**: Tests exercise the running Ripple system exclusively through its external network and process boundaries:
   - **REST API & Doorway Endpoints**: `GET /healthz`, `GET /`, `GET /bootstrap`, `GET /w/:wsId/agent.md`, `GET /api/v1/whoami`, `PATCH /api/v1/me`, `GET /api/v1/snapshot`, `GET /api/v1/context`, `POST /api/v1/invites`, `POST /api/v1/tokens`, `DELETE /api/v1/tokens/:actorId`, `GET|POST /api/v1/items`, `PATCH /api/v1/items/:id`, `POST /api/v1/items/:id/claim`, `GET /api/v1/runs`, `GET /api/v1/runs/:id`, `POST /api/v1/runs/:id/plan`, `POST /api/v1/runs/:id/step`, `POST /api/v1/runs/:id/artifacts`, `POST /api/v1/runs/:id/checkpoint`, `POST /api/v1/runs/:id/heartbeat`, `POST /api/v1/runs/:id/steers`, `POST /api/v1/steers/:id/ack`, `POST /api/v1/runs/:id/takeover`, `POST /api/v1/runs/:id/cancel`, `POST /api/v1/runs/:id/resume`, `POST /api/v1/runs/:id/subruns`, `POST /api/v1/runs/:id/report`, `GET /api/v1/cards`, `POST /api/v1/runs/:id/cards`, `POST /api/v1/cards/:id/answer`, `GET /api/v1/cards/:id/await`, `GET|POST /api/v1/flows`, `POST /api/v1/flows/:id/trigger`, `GET|POST /api/v1/threads/:scopeKind/:scopeId`, `POST /api/v1/integrations/github/pr`, `POST /api/v1/integrations/drive`.
   - **Real-Time SSE Event Stream**: `GET /api/v1/events` with `Last-Event-ID` / `?after=` gapless replay.
   - **Streamable HTTP MCP Server**: `POST /mcp` JSON-RPC 2.0 `tools/list` and `tools/call` across all 18 MCP tools.
   - **CLI Subprocess**: Executing `src/cli.ts` against the live HTTP server URL (`RIPPLE_URL`, `RIPPLE_TOKEN`).
   - **Phone-First Responsive & Desktop Web UI**: `GET /` HTML/CSS/JS verification ensuring identity header, agent invite modal, workspace dialogue room, hierarchical sub-agent tree, backlog board, mobile bottom navigation bar, and zero `prompt()`/`confirm()` calls.
2. **Authoritative Oracle Derivation**: Every test expectation is derived directly from `ORIGINAL_REQUEST.md`, `PROJECT.md § Feature Inventory`, `PROJECT.md § Interface Contracts`, `tandem_PRD.md` (R1–R13), and `tandem_design.md`.
3. **Isolation & Determinism**: Each test suite or scenario boots an isolated HTTP server bound to an ephemeral localhost port (`127.0.0.1:0`, or targets `process.env.RIPPLE_TEST_URL` when validating a live hosted deployment) with a clean `MemoryStore` (and temporary file-backed JSON state path when testing persistence across restarts) and cleans up all sockets and scratch files on teardown.

## 3. Test Architecture & Execution Model

- **Test File**: `/home/antigravity/dweidai/ripple/tests/e2e.test.ts`
- **Framework**: Node.js built-in test runner (`node:test` + `node:assert/strict`) executed via `tsx` (`npx tsx --test tests/e2e.test.ts`).
- **Harness Helper (`startTestWorkspace`)**:
  - Creates an isolated `MemoryStore` (or file-backed `MemoryStore` with a scratch JSON file in `<appDataDir>/scratch/teamwork_tmp/...` when testing persistence), `AuthService`, and `RippleEngine`.
  - Mints initial human token (`you` / `David (@dweidai)`) and starts `createRippleHttpServer(engine, auth)` on an ephemeral port `127.0.0.1:0` (or connects to `process.env.RIPPLE_TEST_URL` if set).
  - Provides opaque-box clients for:
    - `api(path, opts)` — Raw HTTP `fetch` wrapper returning `{ status, headers, data }`.
    - `mcpCall(token, toolName, args)` & `mcpListTools(token)` — Streamable HTTP MCP JSON-RPC 2.0 client parsing `application/json` and `text/event-stream` responses from `POST /mcp`.
    - `runCli(token, args)` — Spawns `node --import tsx src/cli.ts ...` with `RIPPLE_URL` and `RIPPLE_TOKEN` environment variables and captures `{ code, stdout, stderr, json }`.
    - `openSse(token, afterSeq)` — Opens a real HTTP streaming connection to `GET /api/v1/events` and parses incoming SSE frames (`id`, `event`, `data`).

## 4. Tier 4 Real-World Application Scenarios

### Scenario 1 (`T4-S01`): Overnight Phone Workspace — Self-Presence, Inviting Antigravity & Muse, Multi-Agent Dialogue, Backlog Decomposition, Sub-Agent PR & Drive Execution, and Pin-Bound Approval
1. **Phone Login & Self-Presence**: User opens workspace with `?token=`, verifies `GET /api/v1/whoami`, updates profile via `PATCH /api/v1/me` to `David (@dweidai)`, and confirms online presence in `GET /api/v1/snapshot`.
2. **Self-Service Invitation**: User invites **Antigravity (`agy`)** and **Muse (`muse`)** via `POST /api/v1/invites` (with `X-Forwarded-Proto: https` and `X-Forwarded-Host: ripple-demo.trycloudflare.com`), receiving valid tokens and onboarding payloads (`mcpJson`, `doorwayPrompt`, `cliCommand`).
3. **Doorway & Context Discovery**: `agy` and `muse` read `GET /w/ws_default/agent.md?token=...` and invoke MCP `ripple_get_context`.
4. **Multi-Agent Dialogue**: User posts a kickoff message in `workspace/main` mentioning `@muse` and `@agy`. `muse` replies via MCP `ripple_post_message` mentioning `@agy`, and `agy` replies back with an execution proposal.
5. **Collaborative Backlog & Subtasks**: `muse` creates a parent backlog epic via MCP `ripple_create_item` and two subtasks (`parentItemId`) assigned to `muse` (`tags: ['drive', 'spec']`) and `agy` (`tags: ['github', 'code']`).
6. **Parent Runs & Sub-Agent Spawning**:
   - `muse` claims the spec subtask, plans steps, and spawns child sub-run `muse-sub-drive` (`POST /api/v1/runs/:id/subruns`). `muse-sub-drive` attaches a Google Doc artifact (`kind: 'gdoc'`, `https://docs.google.com/document/d/...`) and calls `POST /api/v1/runs/:id/report`, auto-updating the subtask and posting a report to the parent run and workspace dialogue.
   - `agy` claims the engineering subtask, plans steps, and spawns child sub-run `agy-sub-pr` via MCP `ripple_spawn_subrun`. `agy-sub-pr` attaches a commit (`kind: 'commit'`) and GitHub PR (`kind: 'pr'`, `https://github.com/dweidai/ripple/pull/1`) and reports back via MCP `ripple_report_run`.
7. **Pin-Bound Review Gate & Completion**: `agy` raises an `approve` decision card pinned to the PR commit SHA. User answers the card on the matching pin, waking `agy`'s `await`, and `agy` completes the final step, marking the parent run and backlog item `done`.

### Scenario 2 (`T4-S02`): Multi-Agent Contention, Resource Overlap, Mid-Flight Steering, Stale Approval Prevention, and Agent-to-Agent Card Coordination
1. `agy` and `muse` race to claim the same high-priority item; one succeeds (`201`) and the other receives `409 taken`.
2. Both agents claim separate items that touch overlapping files (`touches: ['src/engine.ts', 'src/server.ts']`).
3. User posts a run-scoped dialogue message with `sendToAgent: true` and an urgent steer (`urgency: 'now'`).
4. `agy` receives the urgent steer on `heartbeat` and overlap warnings on `checkpoint`, and acknowledges the steer idempotently.
5. `agy` asks a non-blocking/blocking decision card assigned to `muse` (`assignee: { kind: 'agent', id: 'muse' }`), which `muse` answers via MCP `ripple_answer_card`; attempting a reverse blocking ask while gated is rejected with `409 cycle`.
6. `agy` asks a human review card on commit `sha_v1`, then pushes `sha_v2` before human clicks approve — verifying `c1` auto-stales (`409 stale` if clicked) and human cleanly approves replacement card `c2` on `sha_v2`.

### Scenario 3 (`T4-S03`): Human Takeover Epoch Fencing, Stalled Run Recovery, and Flow Health Strip Lifecycle
1. `agy` starts a run at `epoch = 1`. Human executes `POST /api/v1/runs/:id/takeover`, bumping `epoch = 2` (`status: 'overridden'`) and withdrawing open cards.
2. Delayed zombie writes from `agy` at `epoch = 1` across `step`, `plan`, `checkpoint`, `heartbeat`, and `artifacts` all fail with `409 fenced` (`directive: 'stop'`).
3. A recurring Flow Template (`retryMax: 1`) is triggered, stalls after liveness sweep, auto-recovers at `epoch = 2`, stalls a second time, and raises exactly one deduped escalation card while updating the flow's 14-run health history in `/api/v1/snapshot`.
